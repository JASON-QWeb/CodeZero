# 上下文压缩与最小修改原则

## 1. 为什么需要上下文压缩

Agent 会先在沙箱 clone 完整仓库，但不能把整个仓库都塞进模型上下文。clone 是执行层动作，阅读是检索层动作。系统需要先索引仓库，再通过 agentic search 按需读取，让 Agent 既理解项目，又不被无关文件淹没。

## 2. 上下文分层

### 2.1 L0：任务上下文

- Issue 标题和正文。
- 评论。
- 标签。
- PRD。
- 验收标准。
- 人工审核意见。

### 2.2 L1：项目业务上下文

来自项目业务 skill：

- 业务术语。
- 核心流程。
- 领域规则。
- 权限规则。
- 数据模型说明。

### 2.3 L2：仓库结构摘要

自动生成：

- 目录树。
- package 信息。
- 测试命令。
- 入口文件。
- 框架识别。
- 最近相关改动。

这层只保存摘要和索引引用，不保存完整文件内容。

### 2.4 L3：候选相关文件

通过检索和启发式规则找到：

- 路由文件。
- API handler。
- service。
- model。
- 测试文件。
- 相似功能实现。

候选文件需要证据评分，不能仅凭一次关键词命中进入上下文。

### 2.5 L4：精读文件

只有最相关文件进入完整上下文。大文件优先进入 excerpt 或函数级上下文，除非它本身就是当前修改目标。

### 2.6 L5：Context Pack

最终给实现 Agent 的不是“仓库上下文全集”，而是 `ContextPack`：

- 任务摘要。
- 业务规则。
- 相关文件和证据。
- 相关符号。
- 相关测试。
- 相似历史改动。
- 明确排除的区域。
- 仍未确认的问题。

## 3. 压缩流程

1. 扫描目录结构。
2. 识别技术栈。
3. 加载项目业务 skill。
4. 根据 PRD 生成搜索 query。
5. 使用 `rg`、AST、符号图、embedding、历史 PR 寻找相关文件。
6. 多轮检索并判断证据是否足够。
7. 生成 ContextPack。
8. 选择精读文件。
9. 生成最小修改计划。
10. 对计划进行 scope check。

## 4. 上下文预算

建议默认预算：

- PRD 和验收标准：15%
- 项目业务 skill：20%
- 仓库摘要：15%
- 相关文件代码：35%
- 历史日志和测试输出：10%
- 保留余量：5%

当上下文超预算时，优先保留：

1. 验收标准。
2. 业务规则。
3. 当前要改的文件。
4. 相关测试。
5. 相似实现摘要。

## 5. 最小修改原则

所有实现 Agent 必须遵守：

- 只改满足 PRD 必须修改的文件。
- 不做无关重构。
- 不改格式化无关的大段代码。
- 不改 public API，除非 PRD 明确要求。
- 不引入新依赖，除非计划中说明理由。
- 不修改锁文件，除非安装依赖确实需要。
- 测试只覆盖当前行为，不顺手重写测试体系。

## 6. 最小修改计划格式

```json
{
  "goal": "string",
  "acceptance_criteria": ["string"],
  "files_to_read": ["string"],
  "files_expected_to_change": ["string"],
  "tests_to_add_or_update": ["string"],
  "commands_to_run": ["string"],
  "explicit_non_goals": ["string"],
  "risk_notes": ["string"]
}
```

## 7. Scope Check

实现前检查：

- 计划中的文件是否足够。
- 是否触碰高风险区域。
- 是否需要人工审核。

实现后检查：

- 实际 diff 是否超出计划。
- 是否存在大段无关格式化。
- 是否新增依赖。
- 是否删除测试。
- 是否绕过类型检查。
- 是否修改了 ContextPack 未支持的文件。

## 8. Subagent 审核如何使用压缩上下文

Review subagent 不读取完整仓库，而读取：

- PRD。
- 最小修改计划。
- ContextPack。
- 实际 diff。
- 相关文件摘要。
- 测试结果。
- 截图结果。
- 主 Agent 自评。

这样可以让审核聚焦在“是否满足需求”和“是否改多了”，而不是重新做一遍实现。
